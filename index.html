Closer — working name

A neutral last-mile closure loop for timing and DRC ECOs.

Pre-alpha. There is no improvement claim here.
The loop itself is not implemented. What exists is a rig, a measurement method and two measured results — one of them negative. No customer, no pilot, no PPA claim.

The question

Most of PPA optimisation is automated. The last stretch — post-route timing, DRC and congestion cleanup — is still expert manual work, and it is where tapeouts slip. The question this project tests is narrow:

Given a routed netlist that fails timing or DRC, which function-preserving edit sequence closes the most violation per unit of compute — and can the choice be learned cheaply enough to beat a tuned baseline, reproducibly?

What has actually been measured

On one machine, with an open-source flow (sky130hd/gcd, OpenROAD in a digest-pinned container, no root, ~36 s per RTL→GDS run):

  • The flow is repeatable. Two identical runs produced exactly equal TNS, WNS, hold slack, area and power. Only runtime counters differed.
  • Seed choice is worth ~4%. Five placement seeds gave a 3.7% CV on TNS and a 5.6% spread between the best and the mean seed — with no algorithmic change at all.
  • A promising knob made things worse. Adding post-route setup margin (SETUP_SLACK_MARGIN=0.05) increased TNS by 3.4% on both seeds tested. Turning the TNS repair target to its maximum did nothing, because that is already the default.

The studies behind those numbers live in the repository, with the exact image digest, commands and per-stage metrics. They are noise and negative results, not an improvement claim.

What this changes about the plan

  • Comparisons must be paired per seed: a lucky baseline seed is already ~6% ahead of an average one.
  • Three seeds per arm resolve a 10% effect only because measured noise is ~3.7%; a noisier design needs more, and the measurement has to be repeated per design.
  • Knob names do not predict their effect. Every closure decision has to be measured, which is the entire argument for building a loop that logs what it tried.

What is being built next

  • A post-route ECO loop: classify violations, apply function-preserving edits, re-route, re-measure, accept or revert — every step logged before it runs.
  • A structural audit between netlists. A stand-in for formal equivalence, and labelled as such.
  • Open-source flows first; commercial tools only later, on a customer's licenses.
